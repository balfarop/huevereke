# Reglas de interacción con Notion — límites, eficiencia y sintaxis

Aplica para cualquier skill que lea o escriba las 5 bases documentadas en `notion-schema.md` (`Platos`, `Insumos`, `Receta_Insumo`, `Semanas`, `Semana_Insumo_Familiar`). En un agente vía API (Managed Agents) cada consulta a Notion tiene costo real de tokens, y en este workspace además hay una cuota compartida — en Claude Desktop el costo es menor pero las mismas reglas de límites de la plataforma (no-JOIN, cuota compartida) aplican igual.

## Límites reales de Notion en este workspace

- **No se puede hacer JOIN entre distintas fuentes de datos en una sola consulta SQL** en este workspace (plan no-Business) — `notion-query-data-sources` con más de un `data_source_url` y un JOIN entre ellas falla con "This tool requires a Business plan or higher". Consulta una fuente a la vez y resuelve las relaciones manualmente: trae primero la tabla puente/intermedia (`Receta_Insumo`, `Semana_Insumo_Familiar`) sola, con las URLs de la relación como texto, y si necesitas el nombre legible del otro lado, haz una segunda consulta filtrando por esas URLs.
- **Hay una cuota compartida de todo el workspace para `Query Data Source`** que se agota si se hacen muchas llamadas seguidas (error `"Your workspace has reached the usage limit for Query Data Source"`). Confirmado en producción: **no es un límite de tamaño de una consulta puntual — es un conteo acumulado de llamadas** dentro de una ventana de tiempo, y se puede alcanzar incluso con consultas bien loteadas si son muchas. Ver más abajo la sección específica sobre qué hacer cuando esto pasa.
- Para traer datos de varios elementos a la vez sin JOIN, usa `WHERE Campo LIKE '%url1%' OR Campo LIKE '%url2%' OR ...` en una sola consulta de una sola fuente — esto cumple "por lote, nunca por item" (ver abajo) sin necesitar un JOIN real. Si necesitas columnas de dos fuentes relacionadas (ej. `Receta_Insumo` + `Insumos`), evalúa si de verdad hacen falta ambas consultas o si una sola con las columnas de la tabla puente alcanza para lo que vas a hacer con el dato — cada consulta de más cuenta contra la cuota compartida, sin importar qué tan chica sea.
- **Sí se puede modificar el esquema en vivo** cuando hace falta un campo nuevo que aporte señal real (`notion-update-data-source` con `ADD COLUMN`). Antes de agregar un campo nuevo, confirma con el usuario el diseño (nombre, tipo, opciones) porque es un cambio al esquema compartido que usan varias skills.

## Eficiencia de consultas a Notion

Cuatro reglas, válidas para cualquier consulta:

1. **Por lote, nunca por item.** Si necesitas el mismo dato para varios elementos (varios platos, varios insumos, varias semanas), tráelos TODOS en una sola consulta SQL sobre una sola fuente (`WHERE Campo LIKE '%url%' OR Campo LIKE '%url%' OR ...`) — nunca una consulta por elemento.
2. **Pide solo las columnas que vas a citar o usar**, no la fila completa. Cada columna de más es texto que pagas sin usar.
3. **Si el dato ya está en el hilo de esta conversación, razona con eso — no lo vuelvas a consultar.** Repetir una consulta completa "para empezar de nuevo" paga el mismo dato dos veces.
4. **Agrupa las escrituras nuevas del mismo tipo y mismo destino en una sola llamada** — ej. varias filas nuevas de la misma base en una sola operación de creación, no una por elemento. Esto solo funciona entre páginas con el mismo padre (misma base de datos); no se puede mezclar bases distintas en una llamada.

## Sintaxis SQL de Notion — gotchas confirmados en producción

Estos dos casos causaron consultas fallidas (retries evitables) en una corrida real — verifica esto ANTES de asumir que el problema es otra cosa:

- **Nombres de columna con tilde pueden no coincidir con lo que Notion espera.** Ejemplo real: `SELECT ... "Proteína principal" ...` falló con `validation_error`; la misma consulta sin tilde, `"Proteina principal"`, funcionó. No asumas que el nombre exacto documentado en `notion-schema.md` (que sí lleva tildes, por legibilidad) es literalmente lo que hay que escribir en el SQL — si una consulta falla mencionando una columna, prueba quitando o normalizando los acentos antes de intentar otra cosa, o mejor: usa `notion-fetch` sobre el `data_source_url` para ver el nombre real de la columna tal como Notion lo expone, y cópialo tal cual en vez de escribirlo de memoria.
- **`ORDER BY` sobre una columna de tipo `Date` necesita el cast `"date:NombreColumna:start"`**, no el nombre plano. Ejemplo real: `ORDER BY Fecha DESC` falló con `validation_error`; `ORDER BY "date:Fecha:start" DESC` funcionó.
- **`SELECT` sobre una columna de tipo `Date` también necesita ese mismo cast, no solo `ORDER BY`.** Ejemplo real: `SELECT "Fecha"` junto con `ORDER BY "date:Fecha:start"` falló con `no such column: "Fecha"`; `SELECT "date:Fecha:start" AS "Fecha"` funcionó (usa el `AS` para que la columna de salida se siga llamando como esperas).
- **No asumas que una tabla tiene las mismas columnas que sus tablas relacionadas.** Ejemplo real: se intentó `SELECT ... "Notas" ...` sobre `Receta_Insumo`, que no tiene ese campo (a diferencia de `Platos` e `Insumos`, que sí lo tienen) — la consulta falló y hubo que reintentar sin esa columna, gastando una llamada de más contra la cuota compartida. Antes de escribir un `SELECT`, revisa la lista exacta de columnas de ESA tabla puntual en `notion-schema.md` — no la infieras por parecido con una tabla vecina.
- Si una consulta falla con `validation_error`, no la reintentes a ciegas cambiando cosas al azar — haz un `notion-fetch` sobre ese `data_source_url` primero para ver el esquema real, y arma la consulta corregida en un solo intento con esa información.
- **El lado recíproco de una relación dual (`DUAL` en el DDL de `notion-update-data-source`) no es consultable vía SQL en este workspace, aunque exista y se vea bien en la interfaz de Notion.** Ejemplo real: `Platos.Acompañamientos sugeridos` (Relation → Platos, dual, recíproca `Es acompañamiento sugerido de`) — confirmado que **ningún** plato de toda la base devuelve nada en `Es acompañamiento sugerido de` vía `SELECT`, ni siquiera los que tienen relaciones entrantes reales y verificadas del otro lado. No es una relación rota ni datos perdidos — es una limitación de cómo se indexa esa columna para consultas SQL. **Nunca diseñes una skill que dependa de leer el lado recíproco de una relación dual.** Si necesitas que la relación sea consultable desde ambos lados (ej. un par simétrico donde cualquiera de los dos puede ser el ya-seleccionado), escribe explícitamente ambos lados por separado en el lado *forward* de cada uno (`Acompañamientos sugeridos` propio de cada plato), no confíes en que editar un lado propague algo consultable al otro.

## Qué hacer cuando `Query Data Source` devuelve el error de cuota agotada

Mensaje exacto: `"Your workspace has reached the usage limit for Query Data Source. You can try again later, or start a free trial..."` (el link que ofrece es una promoción de Notion hacia su plan de pago — no es una indicación técnica de que haga falta pagar).

- **Ni bien veas este mensaje exacto una vez en el turno, NINGUNA llamada más a `notion-query-data-sources` en lo que queda de ese turno** — ni la misma consulta que falló, ni otra distinta, ni una versión "más chica" de la misma. Confirmado en producción DOS veces: (1) un reintento idéntico 8 segundos después del primer fallo dio exactamente el mismo error; (2) en otra corrida, después de que las dos primeras consultas del turno fallaran por cuota, se reintentó una de ellas ~5 segundos después (no la misma consulta dos veces seguidas, sino con una consulta distinta de por medio) y también falló igual. La cuota es del workspace completo, no de la consulta puntual ni de la sesión — una vez que aparece este mensaje, ya se agotó para el resto del turno sin importar qué combinación de consultas pruebes después. Trata este mensaje como una señal de "parar de consultar Notion ahora", no como un error transitorio de esa llamada en particular.
- **Sigue adelante con lo que ya tengas** en vez de bloquear toda la tarea por ese dato puntual — es la regla general de "no bloquees el resultado completo por un fallo aislado". Si NINGÚN dato esencial se pudo traer (ej. ni el catálogo de platos ni las últimas semanas), no fuerces una propuesta a medias inventando o asumiendo datos que no llegaste a consultar — en ese caso, dile al usuario en un mensaje breve (sin pegar el link de upsell de Notion ni el texto técnico del error) que la cuota de Notion está agotada por ahora y que puede reintentar más tarde.
- **Si el dato faltante es algo que el resultado final necesita mostrar con precisión** (ej. una cantidad exacta en una lista de compras) pero SÍ tienes lo esencial para avanzar, márcalo explícitamente como no confirmado dentro del propio contenido del resultado (ej. "cantidad: no confirmada") — no lo omitas en silencio, y no lo conviertas tampoco en un mensaje aparte narrando el problema técnico (ver las reglas de formato de salida de la skill que te está usando, si las tiene, para cómo comunicar esto de forma breve).
- **La mejor prevención es mantener bajo el número total de llamadas**, no solo el tamaño de cada una — la cuota es por conteo de llamadas, así que fusionar dos consultas en una cuando sea posible (ver "Eficiencia de consultas" arriba) ayuda aunque no reduzca el volumen de tokens.

## Cómo se leen los archivos de esta skill desde otra skill co-adjuntada

La sintaxis de ruta para que otra skill (ej. `propuesta-menu-semanal`, `analisis-plato-insumo`) lea un archivo de esta skill **depende del entorno** — confirmado con una prueba real:

- **En Claude Desktop:** todas las skills instaladas comparten un directorio local — usa una ruta relativa, ej. `../notion-interaccion/references/notion-schema.md`.
- **En un Managed Agent** (ej. el agente de Telegram) con esta skill co-adjuntada junto a otra: la herramienta `read` exige una **ruta absoluta** — una ruta relativa (con o sin `../`) se rechaza con `invalid_format` ("file_path must be an absolute path"). Ruta confirmada funcionando: `/workspace/skills/notion-interaccion/references/notion-schema.md`.

Como una skill que referencia esta puede correr en cualquiera de los dos entornos, sus propias instrucciones deben intentar primero la ruta relativa (Claude Desktop) y, si falla con un error de formato de ruta, usar la ruta absoluta `/workspace/skills/...` (Managed Agents) — nunca asumir un solo entorno.
